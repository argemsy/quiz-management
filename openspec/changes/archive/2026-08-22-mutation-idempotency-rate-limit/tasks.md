## 4. Idempotency enforcement

- [x] 4.1 Redis fast-path lock added as `src/shared/infrastructure/cache/idempotency_lock.py` (`try_acquire_fast_path_lock`/`release_fast_path_lock`, atomic `SET NX EX`), wired into `mutation_handler.py`'s `async_wrapper` before calling `func`, released in a `finally`. Fails open on Redis errors (same precedent as `AuthMiddleware._is_stale`). `sync_wrapper` only accesses `info.context.operation_id` (enforces the required-header check) without locking — no sync Redis client exists in this codebase and every current mutation is async; documented inline.
- [x] 4.2 Revised during implementation, with user sign-off: a fully generic reflection-based serializer/reconstructor was attempted and found unsafe — `CreateQuizPayload.payload` wraps `QuizType(value: QuizEntity)`, and `QuizEntity.__post_init__` rejects non-`uuid.UUID` id fields, so a naive dict round-trip breaks it. Replaced with "minimal payload + re-fetch": each resolver that wires idempotency decides its own minimal JSON to persist (`create_quiz` stores `{"quiz_id": ...}`) and reconstructs its own payload on replay (re-fetches via `QuizRepository.get_by_id`, reuses the existing `QuizEntity.from_model`) — see `QuizAdminMutation._replay_create_quiz` in `mutations_admin.py`. No generic decorator-level response cache/reconstruct helper was built.
- [x] 4.3 New shared port `IdempotencyReservationRepository` (`src/shared/domain/repositories/idempotency_reservation_repository.py`, `reserve_and_run`/`mark_terminal`/`release`) — user-confirmed location, generalizing the port pattern to cross-cutting infra with no single app owner (mirrors `src/shared/domain/specification.py`'s "shared, no owner" precedent), instead of `quiz` importing `eventing`'s `IdempotencyKey` model directly. Implemented in `src/eventing/infrastructure/repositories/idempotency_reservation_repository_imp.py` (owns the model). `CreateQuizUseCase.execute` now takes `operation_id` and wraps `QuizService.save_sync` (new sync counterpart to `create_quiz`, added to `QuizRepository`/`QuizRepositoryImpl` alongside a new `get_by_id`) in `reserve_and_run`, then calls `mark_terminal(..., SUCCEEDED, {"quiz_id": ...})`. **Known scoping limit**: tenant/tenant_user validation (`TenantValidationService`) and `_validate_questions` still run *before* the reservation (both pre-existing, and the former is a genuine async I/O call that can't run inside the sync `write()` closure) — a retry after one of those failures re-validates fresh rather than replaying a cached error, since no `IdempotencyKey` row exists yet at that point. Only the actual DB write (the literal "no duplicate records" requirement) is covered by the atomic guarantee.
- [x] 4.4 Handled per-resolver, not generically in the decorator (consequence of 4.2's revision): `create_quiz`'s resolver catches `DuplicateOperationError` around `use_case.execute(...)` and dispatches on `exc.status` (`SUCCEEDED` → re-fetch + replay `CreateQuizPayload`; `FAILED_TERMINAL` → replay `ValidationErrorResponse`, not currently reachable per 4.3's scoping note; `IN_PROGRESS` → `IntegrityErrorResponse` "retry shortly").
- [x] 4.5 Three-way policy implemented across the two layers per 4.1-4.4: Redis lock is a pure short-lived mutex (no response stored in it); Postgres `IdempotencyKey.status`/`response_payload` is the durable record, written via `mark_terminal` on success (4.3) — business-error and internal-error paths are not exercised for `create_quiz` today per 4.3's scoping note, so `mark_terminal(..., FAILED_TERMINAL, ...)` isn't called from anywhere yet, and `release` (for internal errors) isn't called anywhere yet either; both exist on the port for the next mutation this pattern gets extended to.
- [x] 4.6 `tests/quiz/presentation/schema/test_create_quiz_idempotency.py` (4 tests, full GraphQL stack via `ASGITransport`): duplicate `operation_id` after success replays the same quiz without a new row; **three concurrent** requests with the same `operation_id` (`asyncio.gather`) produce exactly one row; different `operation_id`s produce separate rows; duplicate detection holds with Redis forced unreachable (monkeypatched, mirrors `test_redis_unreachable_fails_open_and_logs_a_warning`). Business-error and internal-error replay aren't covered here per 4.3/4.5's scoping note — no reachable path to exercise them yet. Full suite: 94/94 passing.
  - **Found and fixed en route (pre-existing, unrelated to idempotency)**: `create_quiz`'s resolver built `CreateQuizDTO` from `strawberry.asdict(input)` directly, but `CreateQuizInput.quiz` is nested (`{"quiz": {"quiz_type": ..., "configuration": ..., "questions": ...}}`) while `CreateQuizDTO` expects those fields flat — the mutation had never been exercised end-to-end via GraphQL (no prior test caught it). Fixed by lifting `input.quiz`'s fields to the top level before validation.
