## Context

See `proposal.md` - Why for motivation. Constraints that shape the approach here:

- `@handle_mutations_exceptions` (`src/shared/presentation/decorators/mutation_handler.py`) already wraps every mutation resolver's full execution — both the success return and every exception path — and is the only place that has `Context.operation_id` today. It's the natural seam for idempotency enforcement; no new decorator or middleware is needed to intercept mutation calls.
- `EventBusMessage.correlation_id` (`src/shared/infrastructure/event_bus/messages.py:21-26`) already exists and already means "ties every message produced while handling the same request/operation together" — the rename in this change makes `Context.correlation_id` match that vocabulary instead of requiring a manual translation at each call site.
- `AuthMiddleware` (`src/shared/presentation/auth_middleware.py`) is the only precedent for a Starlette middleware in this codebase: it fails open on Redis being unreachable (logs a warning, proceeds) and short-circuits with a raw, non-GraphQL `JSONResponse` for its one reject case (`SESSION_STALE`). Both precedents are reused here.
- Redis is already provisioned (`devops/docker-compose.yaml`) and already has one consumer (`PermissionVersionRepositoryImpl`) via `get_redis_client()` — no new infrastructure.
- `devops/docker-compose.yaml` runs `uvicorn` directly, with no reverse proxy in front of it — `request.client.host` is the real TCP peer address; nothing in this deployment sets `X-Forwarded-For` trustworthily today.
- `LoginService.login()` (`src/account/application/login_use_case/service.py`) has zero attempt-throttling today — a clean slate, not a retrofit.
- This is an early-stage, single-frontend project (see `project_early_stage` convention already established for this repo) — no gradual-rollout/back-compat machinery is warranted for the breaking header/field rename.

## Goals / Non-Goals

**Goals:**
- Resolve the `operation_id`/`correlation_id` naming collision so tracing and idempotency stop sharing one field.
- Prevent duplicate business records from a client resubmitting the same logical mutation attempt because it never saw the original response (latency, dropped connection, double-click before UI disables the control) — a UX/latency-driven duplicate, not a hardened defense against a deliberately malicious replayer.
- Make that guarantee hold regardless of Redis's availability — Postgres is the source of truth, Redis is a latency optimization.
- Bound per-IP request volume, with a materially tighter bound specifically on `login`, correctly under concurrent/parallel requests from the same IP (no check-then-write race).

**Non-Goals:**
- Multi-step distributed idempotency across non-transactional side effects (e.g. an external payment call plus a DB write). Not needed: this project's mutations are single ACID Postgres writes, and the event bus is in-process (sync handlers run inline, not over the network), so a multi-state `recovery_point` machine (à la Stripe's production design) would be solving a problem this codebase doesn't have.
- Defense against distributed/adversarial abuse (botnet spreading attempts across many IPs, deliberate IP rotation). This is a single-IP volume throttle, not a WAF or bot-detection layer.
- Frontend key-lifecycle implementation. This change defines the backend contract (header names, retry/regeneration semantics) the frontend must satisfy; implementing that on the frontend is separate work.
- Reverse-proxy-aware IP extraction (`X-Forwarded-For` trust chain). No proxy exists in front of `uvicorn` today; if one is introduced later, IP extraction needs a dedicated follow-up.

## Decisions

**`correlation_id` and `operation_id` become two distinct `Context` properties, both still sourced from client headers, never server-generated.** `correlation_id` (`X-Correlation-ID`) is purely for tracing/log-correlation and flows straight into `EventBusMessage.correlation_id` with no translation. `operation_id` (`X-Operation-ID`) is re-purposed as the idempotency key. Keeping both client-supplied (not server-generated) preserves mandatory pattern #3's original intent — it just now applies to two fields instead of one, and `get_operation_id()`'s dead nanoid generator in `responses.py` is removed rather than repurposed, since server-generating either value would defeat its retry semantics.

**Idempotency enforcement lives in `@handle_mutations_exceptions` (fast path) plus a per-use-case transaction (source of truth) — not in a Starlette middleware.** A middleware sees the POST body as an opaque blob; knowing "is this the `login` mutation" or "does this mutation need idempotency" without parsing the GraphQL document would duplicate what `strawberry`'s executor already does one layer in. The decorator already sits exactly at the mutation-resolver boundary, already receives the relevant id, and already wraps the full success/exception path — extending it is additive, not a new architectural layer. Alternative considered: a GraphQL extension/middleware hook provided by `strawberry` itself — rejected for now since it would require restructuring how mutations are wired for a benefit (framework-native hook vs. decorator) that doesn't change the actual guarantee.

**Redis is a fast path only; a Postgres unique constraint is the actual guarantee.** Lock: `SETNX operation_id` with a short TTL (protects against a crashed worker holding it forever, doesn't gate correctness). Source of truth: a new `idempotency_keys` table (`operation_id` unique) whose insert happens in the same `transaction.atomic()` as the mutation's business write, per use case. A duplicate `operation_id` surfaces as `IntegrityError` on the unique constraint — that's the real arbiter, not the Redis check. Alternative considered: Redis-only lock+replay (the initial plan) — rejected because it cannot guarantee no-duplicate under Redis outage, TTL eviction, or a race window where two near-simultaneous requests both pass `SETNX` before either commits; none of those are exotic edge cases at this codebase's traffic pattern, they're the ordinary latency-retry scenario this change exists to solve. Because Postgres is the real guarantee, `AuthMiddleware`'s fail-open-on-Redis-outage precedent applies here too without weakening correctness — Redis being down just means every request pays the Postgres round-trip instead of skipping it.

**Three-way response-caching policy, not a single cache-everything/cache-nothing rule.** Success and business/validation errors (`DomainError`/`ApplicationError`) are cached under the `idempotency_keys` row and replayed verbatim on a duplicate `operation_id` — both are complete, definitive answers to "what happened to this attempt." Unexpected internal errors (uncaught exception, DB timeout, crash mid-request) are not cached, and the lock is released — the client genuinely doesn't know whether the write happened, so a retry with the same key must actually re-attempt, with the unique constraint deciding the outcome. This determines the frontend contract directly: the client mints a fresh `operation_id` after any terminal response (success or business error), and only reuses the current one when it received no response at all.

**A dedicated `idempotency_keys` table, not a column on every mutable entity.** Alternative considered: put a unique `operation_id` column directly on each entity that mutations create (`Quiz`, etc.) — rejected because it spreads a cross-cutting concern across every present and future domain model instead of centralizing it once in `src/shared/`, and it wouldn't generalize to mutations that don't create a single obvious row (e.g. an update, or a mutation with no persisted output).

**`RateLimitMiddleware` mounts outermost, before `AuthMiddleware`, keyed by `request.client.host` — never a header.** Rate limiting should reject before the cost of JWT decode, matching `AuthMiddleware`'s own "cheapest check first" ordering. `request.client.host` is the real TCP peer address; `X-Forwarded-For` is not used because nothing in this deployment's `docker-compose.yaml` sits in front of `uvicorn` to set it trustworthily — trusting a client-suppliable header here would make the limiter trivially bypassable by rotating that header per request. Revisit if a reverse proxy is introduced (see Non-Goals).

**Two independent rate-limit buckets (general, login), not one shared budget.** A shared budget would let ordinary UI navigation exhaust the allowance meant to catch abuse, and couldn't give `login` the materially tighter bound it needs against credential brute-forcing. The general bucket lives in `RateLimitMiddleware` (transport-level, applies to every request, no GraphQL awareness needed). The login-specific bucket cannot live there without the middleware parsing the GraphQL document to detect the `login` mutation specifically — it lives inside `LoginService.login()` (or its resolver) instead, reusing the same atomic-`INCR` primitive against the same Redis instance under its own key namespace and a lower threshold.

**Atomic `INCR`+`EXPIRE` (fixed window), not check-then-write, for both buckets.** A naive "read counter, compare to limit, then increment" is a TOCTOU race under concurrent/parallel requests from the same IP: two requests can both read a count under the limit before either's increment lands, both passing a check that should have rejected the second. Redis executes commands single-threaded, so `INCR` always returns a correct sequential count regardless of how many requests arrive in parallel — checking the *result* of the increment (not a separate prior read) is what actually closes the race the "DEBEMOS BLINDAR" requirement is about. Fixed window (vs. sliding window/token bucket) is the V1 choice for simplicity — see Risks for the trade-off this accepts.

## Risks / Trade-offs

- [Fixed-window counters allow up to ~2x the nominal limit in a burst straddling a window boundary] → Accepted for V1; the atomic-`INCR` fix already closes the concurrency race that was the actual hardening concern. Upgrade path to a sliding-window counter (weighted current+previous window, same Redis primitives) is available later without changing the external contract if the boundary behavior proves to be a real problem in practice.
- [Redis outage means `RateLimitMiddleware` fails open — temporarily unprotected] → Accepted trade-off, explicit and distinct from the idempotency case: rate limiting has no Postgres-backed fallback, so a Redis outage genuinely removes this protection until Redis recovers. Since `AuthMiddleware` already fails open on the same condition, a Redis outage degrades both protections simultaneously (correlated risk) — worth operational monitoring, not a design gap to close now.
- [The Postgres transaction wrap is manual per use case, not automatically enforced by the decorator] → The decorator can only own the Redis fast path and the generic `IntegrityError` → replayed-response mapping; each use case must wrap its own `idempotency_keys` insert + business write in one `transaction.atomic()`. Document as a required step once implemented (candidate addition to `docs/claude/mandatory-patterns.md`).
- [Replaying a cached response requires serializing arbitrary Strawberry payload/error types and reconstructing them on a cache hit] → Highest-uncertainty implementation piece in this change; needs a generic dict-based serialize/reconstruct helper in the decorator. Flagged for resolution during task breakdown/implementation, not a design blocker.
- [IP-based limiting conflates every client behind a shared IP — NAT, corporate network] → Accepted trade-off for an internal admin tool at this stage; revisit if a legitimate shared-IP lockout incident actually occurs.

## Migration Plan

- New Postgres migration: `idempotency_keys` table (`operation_id` unique, `status`, `response_payload`, timestamps).
- The `operation_id`→`correlation_id` rename and the new `X-Operation-ID` idempotency-key header are a breaking client contract change. No dual-read/back-compat shim: this repo has one consuming frontend and is early-stage (see Context), so backend and frontend ship together rather than through a gradual-rollout window.
- `RateLimitMiddleware` and the login throttle are additive (no schema change) and independent of the idempotency work — deployable on their own if sequencing requires splitting this change.
- Rollback: dropping the middleware registration in `main/asgi.py` and reverting the migration is sufficient for the rate-limit and idempotency-storage pieces in isolation. The rename must roll back together with the frontend — reverting only the backend would break clients already sending the new header/field names.

## Open Questions

- Exact thresholds (N requests, window size) for the general and login rate-limit buckets — implemented as configuration, not hardcoded, so this doesn't change the design, spec, or task breakdown; tunable post-deploy based on observed traffic.
- Cleanup/reaper cadence for `idempotency_keys` rows (working assumption: 24-48h retention, an admin tool doesn't need payment-grade retention) — doesn't affect the table schema or enforcement logic, safe to size later.
